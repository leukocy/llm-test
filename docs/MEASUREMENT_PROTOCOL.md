# 固定工作负载测量协议 `fixed-workload-v1`

本协议覆盖 `concurrency`、`prefill` 和 `matrix` 三类性能测试。
创建页的计划预览、服务端预算校验、执行记录和报告使用同一份条件计划。
其他测试类型仍使用各自的测试方法，计划预览会明确提示尚未接入此协议。

## 工作负载与样本

| 场景 | 负载模型 | 一个条件 | 正式样本数 | 预热样本数 |
| --- | --- | --- | --- | --- |
| 并发阶梯 | 闭环固定并发批次 | 一个并发档位 | 并发数 × 正式轮数 | 并发数 × 预热轮数 |
| 输入长度 | 顺序请求 | 一个输入 token 目标 | 每档请求数 | 每档预热请求数 |
| 吞吐矩阵 | 闭环固定并发批次 | 并发数 × 输入 token 目标 | 并发数 × 正式轮数 | 启用预热时为并发数 |

闭环表示一轮请求完成后才开始下一轮。
这不是指定到达率的开放式负载，也不模拟泊松到达。
我们显式标注负载模型，参考了
[MLPerf Inference 规则](https://github.com/mlcommons/inference_policies/blob/master/inference_rules.adoc)
对 Server、Offline 等负载场景的区分；本平台结果**不声明符合 MLPerf**。

所有档位必须唯一。正式和预热请求合计最多 1000 次。
`max_tokens` 是输出上限，实际生成 token 数需要查看逐请求记录，
不应把上限当作实际输出长度。输入长度同样是目标值，
报告显示成功请求的实际输入 token 中位数；
偏离目标超过 10% 时标记数据质量提示。

## 预热与采集

预热使用相同的并发数、输入 token 目标、输出上限和运行配置，
在各条件正式测量之前执行。预热观测写入任务目录中的 `warmup.csv`，
只含条件、时间、token 数和错误类别；提示词和响应正文不写入该文件。
预热失败会终止测量，避免把预热异常后的结果当成有效正式样本。
矩阵的预热发生在该条件资源峰值采样之前。

预热不计入 `test_results`、正式 CSV、任务正式进度和报告统计。
运行配置记录协议版本、各条件计划、预热计划与实际记录数，
并记录温度、token 计算选项及自定义参数的 SHA-256。
报告核对总正式请求、各条件请求数和预热记录数；
任何不一致会使完整性核验失败。
预热可能改变模型和缓存状态，但当前并发批次仍各自建立 HTTP 客户端，
因此**不能把预热解释为复用测量连接**。

逐请求结果保留实际输入/输出 token、token 来源、计算方法、
TTFT、TPOT、TPS、总时长和错误。
提示词按 UTF-8 计算 SHA-256，指纹进入逐请求元数据与数值导出，
用于核对精确输入；指纹不是脱敏机制，不能代替访问控制。
延迟统计仅使用成功且有限、正值的观测；失败请求仍计入成功率。
详见[指标契约](METRICS_CONTRACT.md)。

## 统计解释

- 报告同时显示正式计划数与每条件实际记录数。
  p50、p95、p99 使用线性插值的经验分位数；
  成功率区间使用 95% Wilson score。
- 条件样本少于 20 时，尾部分位数仅作描述。
  少于约 100 个样本时，p99 没有单百分位的观测分辨率；
  达到 100 也不意味着估计稳定或具备跨模型显著性。
- 同一并发批次中的请求共享系统状态，不能默认视为相互独立。
  档位按配置顺序执行，时间漂移和缓存状态可能与档位混杂。
  严肃比较应重复完整运行、交换或随机化档位顺序，
  并核对硬件、模型版本、参数、token 来源和错误率。
- 当前协议没有开放式到达率控制、稳态检测、跨运行置信区间、
  流式逐 token 时间戳的金标准校验或能耗归因。
  需要这些结论时，应使用相应专门实验设计。
